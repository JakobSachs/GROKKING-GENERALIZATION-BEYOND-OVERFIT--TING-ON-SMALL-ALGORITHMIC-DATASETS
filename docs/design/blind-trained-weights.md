# Blind reading of trained weights

## Goal and scope
Train the repository's original tinygrad transformer, save a genuinely gradient-trained checkpoint, then ask a fresh `openai/gpt-6.1-sol` context what task the weights implement. Sol sees only anonymized numerical tensors and basic architecture details, never the task, source repository, data, scores, hand-written checkpoint, this conversation or agent memory. Preserve all first-attempt evidence, including uncertain/incorrect answers.

## Training protocol
Preserve `transf.py` and `grokking.py` at upstream `5fe20591e86bdde7a2f4323ee0225e28b69ceb39`. A new `train_checkpoint.py` runner uses their actual `Transformer` and `gen_data`, and the original configuration: seed 0, syms 63, context 3, two post-LN unmasked blocks, width128, heads4, FF512, ReLU, dropout0.1 during training. Original task is modulo62 addition over all3844 ordered pairs, random40% training split, batch512, original `nn.optim.AdamW(..., weight_decay=1)` defaults,5000 updates. Random initialize, no manual weights and no pretraining checkpoint. Save initial and final weights, split indices, fixed hyperparameters, progress and train/test loss+accuracy. Do not select a seed/checkpoint by held-out performance or silently extend training. A poorly generalizing checkpoint remains the specimen and is reported honestly. Use CPU first, bounded diagnostics before expensive work; if impractically slow, stop and report timing rather than silently changing model or training settings. Checkpoint final step5000 is saved even if time budget requires a reported partial run; partial runs must be clearly labeled and not submitted as completed5000-step training.

## Blind interface
Export every final weight tensor with generic architectural keys to a neutral `specimen.npz`; a separate generic `architecture.json` describes matrix conventions, position/token embedding layout and the original forward operations. No operand meaning, arithmetic vocabulary, separator label, training hyperparameters, train/test scores, task labels or identifying paths in the supplied content. Architecture may disclose raw dimensions and that final-position logits classify token IDs; those are legitimate architectural clues, not proof of weight interpretation.

A fresh explicit `ModelRuntime.completeSimple` context, no coding-agent resource discovery/history, selects exactly `openai/gpt-6.1-sol` and a unique session ID. Existing provider-managed credentials only; never log, copy or print tokens/headers. Save the exact system/user/tool schemas and all model/tool messages before interpreting its answer. No automatic retry/cherry-picking on failed or unhelpful guesses.

The model can request named tensor data/summary/slices and bounded matrix algebra on weights through a purpose-built numerical interface, not arbitrary host files, shell, internet, model forward passes or training. Architecture-only initial guess is recorded before numerical evidence if requested, so we can distinguish dimensions-based guesses from actual weight-based evidence. Bound tool calls to20, output per call to12000characters, wall time20minutes and model token budget per response. Its final answer must rank task hypotheses, state confidence/uncertainty and cite numerical evidence. No options list that gives away the true task. A tool failure is not interpreted as scientific failure; preserve and report setup failures separately.

## SDK logging boundary
The installed `pi-ai/dist/api/openai-responses.js` constructs its API client with credentials/headers separately, then calls `onPayload(params, model)` on the JSON request body (lines117–126). `buildParams` contains model/input/tools/reasoning/sampling options, not authentication (lines239–291). The returned result is a normalized `AssistantMessage` initialized with role/content/provider/model/usage/stopReason/timestamp (lines98–114), not the HTTP response object. The harness does not register `onResponse` or log `getAuth` results. Thus request-body and normalized-message logging exclude credential headers. No credential contents were read or printed during this audit. Prior/final text files use exclusive creation. Refusing an existing run directory happens before new run logging intentionally, so it cannot overwrite the original run's status or guess.

## Integrity and checks
Before the first Sol request, commit/freeze checkpoint, export, architecture and exact prompt hashes in a private manifest. Verify final tensors differ from initialization and exported tensors exactly match final trained parameters. Keep trained artifacts and task-bearing metrics outside the model-facing tool implementation. The blind process exposes only numerical tools; model text must never become a host shell command. Unit tests cover no-leak prompts/tools, tensor bounds, prohibited operations and serialization. Run a separate independent review of the final prompt/tool context before the first call.

## Interpretation
This is one exploratory blind identification, not a benchmark. The tiny three-token architecture itself strongly suggests a synthetic classification task; report any architecture-only guess separately. Correctness from guesses alone does not establish mechanistic understanding. Sol's answer is frozen before task disclosure or follow-up testing. No deployment or edits to the previous hand-written-weight PR. New work lives on `experiment/blind-trained-weights` in its own worktree.
